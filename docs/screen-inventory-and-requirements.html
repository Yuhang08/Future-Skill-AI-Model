1. Scope and evidence standard

This deliverable: screen inventory and user requirements. No application code, dependencies, runtime settings, or workflows were changed. No Figma file was supplied or edited.

Method: static inspection of the HTML, JavaScript, API, scheduling logic, persistence, README, and existing integration tests. Screens described here were not rendered or interactively verified; existing tests were read, not run. “Present in source” is not a claim that a feature has passed testing.

  • Observed: behavior or content directly present in the imported code.
  • Gap: a mismatch or missing capability identified by inspection, requiring confirmation or implementation.
  • Proposed: a recommended future requirement, not a shipped feature or an approved design.
Product limits: this is a rule-based prototype, not a trained AI system, validated career suitability assessment, verified skills test, or employment guarantee. The learning tree is a motivational UI, not evidence of environmental impact.

Deferred deliverables: UI changes, Figma editing, fuller system-interface specification, learning-path redesign, SDG mapping, integrated documentation, and pitch deck. This document provides their baseline; it does not claim to complete them.

2. Users and core journeys

Observed user categories: student/fresh graduate; currently employed; planning a career change; returning to work or learning. These are profile choices, not different permission roles. No administrator, teacher, employer, or authenticated account interface is present.

Discover a direction: landing → 24 interest questions → 12 subject questions → 6 broad skill ratings → career results → choose a reskilling link.

Already have a goal: direct reskilling entry → choose one of five example careers and enter profile → rate specific skills → set schedule → generate pathway.

Continue learning: return with the same browser-session identity → saved dashboard → select week → complete/reopen a task → add or replace a photo → adjust timetable or edit profile.

User needs

  • Explore career directions with understandable reasons rather than promises of success.
  • Understand which self-rated skills differ from an illustrative career target.
  • Get manageable learning activities that fit available time and study days.
  • Record effort and adjust availability without losing completed work.
  • Understand what data is saved, who can see it, and the limits of the prototype.

7. Gaps and recommended priorities

  1. High — returning-user career handoff. Query handling sits inside the “no saved profile” condition. A nested saved-profile switching branch is therefore unreachable. A recommendation link can leave a returning learner on the prior pathway without explaining the new target. Proposed: explicit keep/switch choice with skill reassessment before saving.
  2. High — explain data replacement. Regeneration removes unfinished task records and their evidence. Proposed: a clear impact notice and deliberate confirmation before replacing work.
  3. High before public launch — privacy and identity. The README explicitly warns against public deployment as-is. Retention/deletion, account recovery, secure cookies, stronger uploads, rate limiting and durable private storage remain launch requirements.
  4. Medium — startup and error recovery. Catalog/session load failure has a short-lived toast but no explicit retry control. Proposed: persistent error panel and disabled dependent actions.
  5. Medium — empty state accuracy. No-gap profiles can be shown a congratulatory “all tasks completed” message despite never having tasks. Separate “no gaps by self-rating” from “completed schedule.”
  6. Medium — consistent interface and accessibility. Two page families use separate styling. Responsive CSS exists, but keyboard, screen-reader, contrast, touch and rendered layout checks remain unverified.
  7. Medium — progress history. Only fourteen recent completed wins are rendered. A full history and evidence deletion are not available in the current UI.

Not included in this baseline: labor-market forecasting, automatically graded photos, certifications, external learning-provider integrations, teacher/admin consoles, payments, or measured SDG outcomes. These must not be presented as implemented.

Decisions still needed before broader work

  • Is the next release a classroom/local demo or intended for real public learners?
  • Which learner group and primary journey should the redesign prioritize?
  • Is there an existing Figma file, editable link, design system or branding to preserve?
  • Which institution/project rubric, document format and pitch audience apply?
  • For SDG mapping, which features are intended contributions and which outcomes will actually be measured? Do not infer impact from the learning-tree graphic.

SDG mapping and the pitch deck should reference approved requirements and evidence from this baseline, while labeling illustrative targets, proposed features and unmeasured outcomes honestly.
